# SeatyReservation

Phoenix application for theatre seat reservations (Südtiroler Volksbühne).

Guests reserve seats for performances and receive a private reservation link by email. Staff manage events and reservations through an authenticated admin interface.

## Stack

- Elixir
- Phoenix 1.7
- Ecto + SQLite
- LiveView
- Swoosh
- Tailwind + esbuild
- Gettext (`de`, `en`)

## Architecture

Follow standard Phoenix conventions.

### Business (`lib/seaty_reservation/`)

Contexts own:

- business rules
- persistence
- queries
- changesets
- email orchestration

Primary contexts:

- `Events`
- `Reservations`
- `Allocations`
- `Productions`

### Web (`lib/seaty_reservation_web/`)

Contains:

- controllers
- LiveViews
- components
- routing

Controllers delegate business logic to contexts.

### Rules

- Controllers never contain business logic.
- Schemas define fields, associations, and changesets only.
- Extend existing contexts before creating new ones.
- Prefer conventional Phoenix and Ecto patterns over custom abstractions.

## Domain Rules

### Event

A theatre performance with:

- date
- `total_seats`
- `active`

An event has many reservations.

### Production

A grouping for events with:

- `name`

An event belongs to a production (required). Deleting a production cascades to its events and related reservations.

### Reservation Code

Generated by `Reservations.get_next_code/1`:

```elixir
event_id * 1000 + count
```

Reservation codes are unique within an event.

### Priority

- Lower numbers represent higher priority.
- New reservations receive `min(existing_prio) - 5`.
- Cancelled reservations always have `prio = 0`.

### Guest Access

Guests access reservations via:

```text
/reservations/:id?token=...
```

using a randomly generated 32-character token.

There is no guest login.

### Cancellation

Cancellation is always a soft cancel:

- `seats = 0`
- `prio = 0`
- `internal_comment = "storniert"`
- send cancellation email

### Capacity

Reservations may never exceed available seats.

Both creation and updates enforce:

```text
reserved + requested <= total_seats
```

Seat allocation is handled by the `Allocations` context. Allocations are persisted to the database and can be created, viewed, and deleted through the event detail page.

## Development

When implementing changes:

1. Extend an existing context whenever appropriate.
2. Follow nearby implementations before introducing new patterns.
3. Keep changes minimal and localized.
4. Keep controllers thin.
5. Add or update tests.
6. Preserve existing public APIs unless explicitly changing them.

Before considering work complete:

```sh
mix format
mix test
```

Schema changes require an Ecto migration.

Customer-facing text must use Gettext with both German and English translations.

## Important Files

- `README.md` — setup and deployment

## Constraints

Never:

- commit secrets
- remove the capacity guard
- expose admin functionality outside the `:auth` pipeline
- edit generated assets under `priv/static/assets`

Always:

- create an Ecto migration for schema changes
- preserve reservation links
- keep guest access token-based
- use `SY_` environment variables for runtime configuration
